# บทที่ 2 แนวคิด ทฤษฎี และเอกสารที่เกี่ยวข้อง

บทนี้กล่าวถึงหลักการของระบบฝังตัวและเทคโนโลยีที่เกี่ยวข้องกับหุ่นยนต์ส่งอาหาร โดยเน้นการควบคุมมอเตอร์ด้วยไมโครคอนโทรลเลอร์ การอ่านข้อมูลจาก encoder และเซนเซอร์ การคำนวณการเคลื่อนที่ การสื่อสารระหว่างอุปกรณ์ และกลไกความปลอดภัย เนื้อหาแต่ละส่วนเชื่อมโยงกับการทำงานที่ปรากฏใน firmware และซอฟต์แวร์ของโครงงาน ส่วนรายละเอียดการติดตั้งอุปกรณ์ การพัฒนาโปรแกรม และผลการทดสอบควรนำเสนอในบทที่ 3 และบทที่ 4 ตามลำดับ

## 2.1 ระบบฝังตัวและสถาปัตยกรรมของหุ่นยนต์

### 2.1.1 แนวคิดของระบบฝังตัว

ระบบฝังตัว (embedded system) คือระบบคอมพิวเตอร์ที่ประกอบด้วยฮาร์ดแวร์และซอฟต์แวร์ซึ่งออกแบบมาเพื่อทำหน้าที่เฉพาะ เช่น อ่านค่าจากเซนเซอร์ ประมวลผลตามเงื่อนไข และสั่งงานอุปกรณ์เอาต์พุต ระบบประเภทนี้ต้องพิจารณาทั้งความถูกต้องของผลลัพธ์ เวลาที่ใช้ตอบสนอง ข้อจำกัดด้านหน่วยความจำและพลังงาน ตลอดจนพฤติกรรมเมื่อเกิดความผิดพลาด

ไมโครคอนโทรลเลอร์รวมหน่วยประมวลผล หน่วยความจำ และวงจรต่อพ่วง เช่น GPIO, timer, PWM, interrupt และ serial interface ไว้ในชิปเดียว Arduino Uno R3 ซึ่งใช้ ATmega328P มีขา I/O สำหรับเชื่อมต่ออุปกรณ์และทรัพยากรฮาร์ดแวร์สำหรับนับเวลา สื่อสาร และสร้างสัญญาณ PWM [1], [2] ความสามารถเหล่านี้เหมาะกับงานที่ต้องอ่าน encoder และปรับสัญญาณควบคุมมอเตอร์เป็นช่วงเวลาสม่ำเสมอ

คอมพิวเตอร์บอร์ดเดี่ยว (single-board computer: SBC) เช่น Raspberry Pi มีระบบปฏิบัติการและทรัพยากรการประมวลผลมากกว่าไมโครคอนโทรลเลอร์ จึงสะดวกต่อการทำงานระดับสูง เช่น การจัดการภารกิจ การเชื่อมต่อส่วนติดต่อผู้ใช้ และการประมวลผลซอฟต์แวร์หุ่นยนต์ ทั้งนี้ การทำงานบนระบบปฏิบัติการทั่วไปไม่ได้รับประกันเวลาตอบสนองแบบ hard real-time โดยอัตโนมัติ การแยกงานควบคุมมอเตอร์ที่ต้องทำซ้ำตามคาบไปไว้บนไมโครคอนโทรลเลอร์จึงช่วยให้การแบ่งหน้าที่ชัดเจนขึ้น

### 2.1.2 การแบ่งหน้าที่ในโครงงาน

ระบบปัจจุบันแบ่งงานระหว่าง Arduino Uno R3 หนึ่งบอร์ดกับ Raspberry Pi 4 Model B หน่วยความจำ 4 GB Arduino อ่าน Encoder, ควบคุมมอเตอร์ซ้าย–ขวาผ่าน L298N, แสดงลูกศรเลี้ยวบน LED Matrix 32x8 และอ่าน Keypad 4x4 ผ่าน PCF8574 ทาง I2C ส่วน Raspberry Pi รัน POS/Kiosk, จัดการภารกิจและ waypoint, รับข้อมูล LiDAR และเชื่อมต่อกับ Arduino ผ่าน USB Serial/ROS 2

จอสัมผัส POS/Kiosk เป็นส่วนติดต่อผู้ใช้หลัก Keypad เป็นอินพุตทางเลือกที่แก้ POS draft และสถานะภารกิจชุดเดียวกัน ระบบปัจจุบันไม่มี Arduino ตัวที่ 2, IR sensor, LCD ตัวอักษรแยก หรือปุ่ม Manual Override รายละเอียดอุปกรณ์และ pinout อ้างอิงได้จาก [แบบออกแบบฮาร์ดแวร์](design.md), [firmware ควบคุมการเคลื่อนที่](../src/Arduino_1_Motion/Arduino_1_Motion.ino) และ [จุดเริ่มต้นระบบหลัก](../src/main.py)

## 2.2 อินพุต เอาต์พุต และการควบคุมมอเตอร์

### 2.2.1 GPIO, interrupt และ PWM

GPIO (general-purpose input/output) ใช้รับหรือส่งสัญญาณดิจิทัล เช่น อ่านสถานะปุ่มและเซนเซอร์ หรือกำหนดทิศทางการหมุนของมอเตอร์ การอ่านอินพุตเป็นช่วง ๆ เหมาะกับสัญญาณที่เปลี่ยนไม่บ่อย แต่สัญญาณ encoder อาจเกิดพัลส์ต่อเนื่องระหว่างที่โปรแกรมทำงานส่วนอื่น การใช้ interrupt ทำให้ไมโครคอนโทรลเลอร์ตอบสนองต่อการเปลี่ยนแปลงของขาอินพุตและปรับตัวนับพัลส์ได้โดยไม่ต้องรอการวนอ่านตามลำดับปกติ [2], [3]

โครงงานใช้ Pin Change Interrupt บนพอร์ต C ของ ATmega328P สำหรับ encoder โดยตรวจขอบขาขึ้นของสัญญาณเฟส A และอ่านระดับของเฟส B เพื่อกำหนดทิศทางการนับ การอ่าน tick จากตัวนับที่เปลี่ยนใน interrupt ต้องทำอย่างปลอดภัย เช่น ปิด interrupt ชั่วคราวขณะคัดลอกค่าหลายไบต์ เพื่อป้องกันการอ่านค่าครึ่งเก่าครึ่งใหม่

PWM (pulse-width modulation) ควบคุมกำลังเฉลี่ยที่ส่งให้โหลดด้วยการปรับสัดส่วนเวลาที่สัญญาณอยู่ระดับสูงต่อหนึ่งคาบ หรือ duty cycle สำหรับ Arduino Uno ฟังก์ชัน `analogWrite()` ใช้สร้างเอาต์พุต PWM บนขาที่รองรับ ไม่ใช่การสร้างแรงดันแอนะล็อกจริง [3] ในโครงงาน firmware ใช้ PWM ที่ขา enable ของวงจรขับมอเตอร์ และใช้ขาดิจิทัลอีกชุดกำหนดทิศทาง

### 2.2.2 มอเตอร์กระแสตรงและวงจร H-bridge

มอเตอร์กระแสตรง (DC motor) เปลี่ยนพลังงานไฟฟ้าเป็นการหมุนของเพลา ความเร็วและแรงบิดขึ้นกับแรงดัน กระแส โหลดเชิงกล และคุณสมบัติของมอเตอร์ การกลับขั้วแรงดันที่ขั้วมอเตอร์ทำให้เปลี่ยนทิศการหมุน แต่ขาไมโครคอนโทรลเลอร์ไม่ควรจ่ายกระแสให้มอเตอร์โดยตรง จึงใช้วงจรขับกำลังเป็นตัวกลาง

H-bridge เป็นวงจรสวิตช์ที่กลับทิศทางแรงดันที่ขั้วมอเตอร์ได้ วงจร L298 เป็น dual full-bridge driver ที่ออกแบบมาสำหรับโหลดเหนี่ยวนำ เช่น มอเตอร์ DC [4] ในโครงงาน Arduino ส่งสัญญาณกำหนดทิศทางและ PWM ไปยัง L298 เพื่อควบคุมล้อซ้ายและขวาแยกกัน ข้อมูลกระแสและความสามารถในการขับโหลดของโมดูลจริงควรอ้างอิง datasheet ของชิ้นส่วนและตรวจสอบกับอุปกรณ์ที่ใช้ ไม่ควรอนุมานจากชื่อโมดูลเพียงอย่างเดียว

### 2.2.3 Encoder และการวัดความเร็ว

Rotary encoder สร้างพัลส์ตามการหมุนของเพลา เมื่อนับจำนวนพัลส์ในช่วงเวลาที่ทราบ สามารถประมาณความเร็วได้ และเมื่อนับการเปลี่ยนแปลงของพัลส์สะสม จะประมาณระยะทางที่ล้อเคลื่อนที่ได้ สำหรับล้อรัศมี (R) และ encoder ความละเอียด (N) tick ต่อรอบ ระยะทางต่อ tick โดยประมาณคือ

\[
\Delta s_{tick}=\frac{2\pi R}{N}
\]

หากนับได้ \(\Delta n\) tick ระยะที่ล้อเคลื่อนที่คือ \(\Delta s=\Delta n\,\Delta s_{tick}\) และความเร็วเฉลี่ยในช่วงเวลา \(\Delta t\) คือ \(v\approx\Delta s/\Delta t\) [6] โครงงานกำหนดค่ารัศมีล้อ \(R=0.065\,m\) และความละเอียด \(N=1920\,ticks/rev\) จึงได้ระยะทางเชิงทฤษฎีประมาณ \(0.000213\,m/tick\) ค่านี้ขึ้นกับความละเอียดจริงของ encoder และการนับขอบสัญญาณตาม firmware

### 2.2.4 การควบคุมความเร็วแบบป้อนกลับ

การควบคุมแบบป้อนกลับ (feedback control) เปรียบเทียบค่าที่ต้องการกับค่าที่วัดได้ แล้วนำความคลาดเคลื่อนไปคำนวณคำสั่งควบคุม ตัวควบคุม PID ประกอบด้วยส่วนสัดส่วน (P) ส่วนอินทิกรัล (I) และส่วนอนุพันธ์ (D) ซึ่งเขียนในรูปแบบต่อเนื่องอย่างย่อได้ว่า

\[
u(t)=K_p e(t)+K_i\int_0^t e(\tau)\,d\tau+K_d\frac{de(t)}{dt}
\]

โดย \(e(t)=r(t)-y(t)\) คือผลต่างระหว่างค่าเป้าหมายกับค่าที่วัดได้ ส่วน P ตอบสนองต่อความคลาดเคลื่อนปัจจุบัน ส่วน I สะสมความคลาดเคลื่อนในอดีต และส่วน D ตอบสนองต่ออัตราการเปลี่ยนแปลงของความคลาดเคลื่อน [5] ในการใช้งานดิจิทัลจะประมาณอินทิกรัลและอนุพันธ์จากตัวอย่างตามช่วงเวลา และต้องพิจารณาการจำกัดเอาต์พุตกับ integral windup เมื่อคำสั่งขับถึงขีดจำกัด

firmware ของ Arduino หมายเลข 1 คำนวณความเร็วจาก encoder ในรอบควบคุมทุกประมาณ 20 ms หรือ 50 Hz ใช้ตัวควบคุม PID แยกสำหรับล้อซ้ายและขวา มีการกรองความเร็วที่วัดได้ จำกัดผลรวมอินทิกรัล และเพิ่ม feed-forward ตามความเร็วเป้าหมาย นอกจากนี้ยังปรับ setpoint ของแต่ละล้อจากความต่างของระยะที่ล้อเคลื่อนที่ เพื่อช่วยลดการเบี่ยงเบนขณะวิ่งตรง เมื่อไม่พบการหมุน encoder ตามคำสั่ง ระบบเพิ่มแรงขับเป็นขั้นภายในขอบเขต และยก fault หากไม่พบการเคลื่อนที่ต่อเนื่อง

การเร่งและลดความเร็วอย่างค่อยเป็นค่อยไปช่วยลดการเปลี่ยนโหลดเชิงกลฉับพลัน ส่วนการลดความเร็วเมื่อใกล้ระยะเป้าหมายช่วยลดโอกาสเลยจุดหยุด ทั้งสองแนวทางเป็นส่วนหนึ่งของการควบคุมการเคลื่อนที่ของ firmware แต่ค่าที่ใช้จริงและผลต่อความแม่นยำควรรายงานจากการทดสอบในบทที่ 4

## 2.3 การเคลื่อนที่แบบ Differential Drive และ Odometry

หุ่นยนต์แบบ Differential Drive ใช้ล้อขับเคลื่อนสองข้างที่ควบคุมความเร็วแยกกัน เมื่อกำหนดให้ \(v_L\) และ \(v_R\) เป็นความเร็วเชิงเส้นของล้อซ้ายและขวา และ \(b\) เป็นระยะห่างระหว่างล้อ ความเร็วเชิงเส้นของจุดกึ่งกลางหุ่นยนต์ \(v\) และความเร็วเชิงมุม \(\omega\) มีความสัมพันธ์ดังนี้

\[
v=\frac{v_R+v_L}{2},\qquad
\omega=\frac{v_R-v_L}{b}
\]

เมื่อความเร็วล้อเท่ากัน หุ่นยนต์จะเคลื่อนที่ตรงโดยประมาณ เมื่อความเร็วต่างกันจะเกิดการเลี้ยว และเมื่อหมุนล้อสวนทางกันด้วยขนาดใกล้เคียงกันจะหมุนรอบตัวเองได้ รูปแบบนี้เหมาะกับหุ่นยนต์ที่ต้องเลี้ยวในพื้นที่จำกัด แต่ความแม่นยำขึ้นกับรัศมีล้อ ระยะห่างล้อ และการสัมผัสพื้น

Odometry คือการประมาณตำแหน่งและทิศทางจากการเคลื่อนที่สะสมของล้อ สำหรับช่วงเวลาหนึ่ง คำนวณระยะล้อซ้ายและขวา \(\Delta s_L\), \(\Delta s_R\) แล้วหา

\[
\Delta s=\frac{\Delta s_R+\Delta s_L}{2},\qquad
\Delta\theta=\frac{\Delta s_R-\Delta s_L}{b}
\]

ตำแหน่งใหม่ประมาณได้ด้วยวิธี midpoint ดังนี้

\[
x_{k+1}=x_k+\Delta s\cos(\theta_k+\Delta\theta/2),\quad
y_{k+1}=y_k+\Delta s\sin(\theta_k+\Delta\theta/2),\quad
\theta_{k+1}=\theta_k+\Delta\theta
\]

ในโครงงาน Raspberry Pi คำนวณ odometry จากข้อมูล tick ซ้ายและขวาที่ Arduino ส่งมา โดยใช้พารามิเตอร์รัศมีล้อและระยะห่างล้อที่กำหนดไว้ใน configuration การประมาณแบบนี้เป็น dead reckoning จึงมีความคลาดเคลื่อนสะสมจากการลื่นไถล ความต่างของขนาดล้อ ความคลาดเคลื่อนของจำนวน tick และการสอบเทียบระยะห่างล้อ งานของ Borenstein และ Feng อธิบายแหล่งความคลาดเคลื่อนเชิงระบบที่สำคัญ รวมถึงผลของ effective wheelbase และเส้นผ่านศูนย์กลางล้อที่ไม่เท่ากัน [6]

ในโค้ดระบบหลัก เส้นทางส่งอาหารใช้ waypoint และ odometry จากล้อเป็นข้อมูลตำแหน่ง โดยแผนที่ร้านอาหารใช้แสดงผล ไม่ได้เป็นแหล่ง localization ของ route controller ตามที่ระบุไว้ใน [main.py](../src/main.py) ส่วน [slam_bridge.py](../src/slam_bridge.py) เป็น bridge แยกสำหรับการทดสอบ ROS 2/SLAM ดังนั้นควรอธิบาย SLAM เป็นระบบทดสอบหรืองานต่อยอด เว้นแต่การสาธิตของโครงงานจะใช้ SLAM ในภารกิจจริง

## 2.4 เซนเซอร์และการตรวจจับสิ่งกีดขวาง

### 2.4.1 Keypad 4x4 และตัวขยายพอร์ต PCF8574

Keypad 4x4 เป็นอุปกรณ์ป้อนคำสั่งจากผู้ใช้ แป้นแบบเมทริกซ์จัดปุ่มเป็นแถวและคอลัมน์ ส่วน PCF8574 ทำหน้าที่เป็นตัวขยายพอร์ต I/O แบบดิจิทัลและสื่อสารกับ Arduino Uno ผ่าน I2C โดยใช้ SDA ที่ A4, SCL ที่ A5 และ address เริ่มต้น 0x20 ตาม firmware ของโครงงาน [Arduino1Keypad.h](../src/Arduino_1_Motion/Arduino1Keypad.h) กำหนด Row ไปยัง P7–P4 และ Column ไปยัง P3–P0

Arduino ส่งตัวอักษรจากปุ่มที่กดไปยัง Raspberry Pi ผ่าน Serial ในรูปแบบ KEY:<ปุ่ม> ผู้ใช้ใช้ Keypad เลือกชั้นและโต๊ะ ยืนยันอาหารที่วางด้วยตนเอง เริ่มงาน และยืนยันรับอาหารที่โต๊ะ Keypad ไม่ได้ตรวจว่ามีอาหารวางหรือถูกหยิบออกจากชั้น

### 2.4.2 LiDAR และเขตหยุดเพื่อความปลอดภัย

LiDAR แบบระนาบวัดระยะตามมุมหลายทิศทาง ข้อมูลสแกนประกอบด้วยค่าระยะ มุมเริ่มต้น มุมสิ้นสุด และมุมที่เพิ่มขึ้นต่อหนึ่งตัวอย่างตามรูปแบบ `sensor_msgs/LaserScan` [7] การใช้ข้อมูลดังกล่าวอาจมีได้หลายระดับ ตั้งแต่การแสดงสภาพแวดล้อม การสร้างแผนที่ ไปจนถึงการตรวจเขตอันตรายเฉพาะหน้า

ใน [lidar_safety.py](../src/lidar_safety.py) โครงงานมี LiDAR safety guard ที่เลือกพิจารณาลำแสงในกรวยด้านหน้าหุ่นยนต์ กรองค่า NaN, infinity และระยะที่อยู่นอกช่วงที่ใช้ จากนั้นตรวจว่ามีจุดระยะใกล้ในเขตที่กำหนดอย่างน้อยสามจุดหรือไม่ ค่าเริ่มต้นของซอฟต์แวร์กำหนดกรวยด้านหน้า ±35 องศา ระยะหยุด 0.30 m และระยะตัดค่าที่ใกล้ตัวหุ่นยนต์ 0.22 m โดยปรับระยะหยุดผ่าน environment variable ได้ เมื่อพบสิ่งกีดขวาง waypoint controller จะหยุดส่งความเร็วเดินหน้าและรอให้ทางโล่งก่อนดำเนินต่อ การทำงานขณะใช้งานจริงต้องมี ROS 2 และ LiDAR driver ที่ส่งข้อมูล `/scan` ให้ node ใน [main.py](../src/main.py)

กลไกนี้เป็น virtual bumper สำหรับการหยุดตามเขตระยะที่กำหนด ไม่ใช่ระบบตรวจจับวัตถุหรือระบบนำทางอัตโนมัติเต็มรูปแบบ การประเมินความปลอดภัยจริงยังต้องทดสอบกับวัตถุ พื้นผิว ระยะติดตั้ง และความเร็วของหุ่นยนต์ที่ใช้

## 2.5 การสื่อสารและการจัดการสถานะ

### 2.5.1 Serial communication ระหว่างอุปกรณ์

Serial communication ส่งข้อมูลเป็นลำดับบิตผ่านช่องสื่อสาร โดยผู้ส่งและผู้รับต้องกำหนดอัตราส่งข้อมูลและรูปแบบข้อมูลให้ตรงกัน ฟังก์ชัน <code>Serial.begin()</code> ใช้กำหนด baud rate [3] Arduino ของโครงงานสื่อสารกับ Raspberry Pi ผ่าน USB Serial ที่ 115200 baud และใช้ newline แบ่งกรอบข้อมูล

Firmware ส่ง <code>ENCODER:&lt;left&gt;,&lt;right&gt;</code>, สถานะ <code>STATUS:</code> และเหตุการณ์ปุ่ม <code>KEY:&lt;char&gt;</code> ส่วน Pi ส่งคำสั่งเคลื่อนที่และคำสั่งไฟเลี้ยวกลับไปยัง Arduino เมื่อใช้ ROS 2, <code>slam_bridge.py</code> อ่าน KEY จาก Serial แล้วส่งต่อด้วย ROS topic <code>/keypad/key</code>; <code>main.py</code> ส่ง event ให้ POS Server ตีความตามสถานะภารกิจ หากใช้ backend แบบ Serial โดยตรง <code>odometry.py</code> จะส่ง key event ให้ POS โดยตรง จอ POS ติดต่อ POS Server ผ่าน HTTP และใช้ draft ร่วมกับ Keypad ไม่มีโปรโตคอล IR, LCD หรือ Arduino ชั้นวางในฮาร์ดแวร์รุ่นปัจจุบัน

### 2.5.2 Finite State Machine และการทำงานตามเวลา

Finite State Machine (FSM) แทนการทำงานเป็นชุดสถานะและเงื่อนไขเปลี่ยนสถานะ เหมาะกับกระบวนการที่มีลำดับชัดเจน เช่น รอรับคำสั่ง เริ่มเดินทาง ถึงโต๊ะ รอรับอาหาร ตรวจรายการที่เหลือ และกลับสถานี FSM ระดับภารกิจใน [delivery_fsm.py](../src/delivery_fsm.py) จึงแยกจากสถานะควบคุมการเคลื่อนที่ใน firmware ได้ โดยแต่ละระดับรับผิดชอบคนละขอบเขต

การทำงานแบบไม่บล็อก (non-blocking) หมายถึงการตรวจว่าถึงเวลาทำงานหรือยังโดยไม่หยุดรอจนกว่างานหนึ่งจะเสร็จ เช่น ใช้ `millis()` เปรียบเทียบเวลาปัจจุบันกับเวลารอบควบคุม วิธีนี้เปิดโอกาสให้โปรแกรมอ่านอินพุต อัปเดตสถานะ และควบคุมมอเตอร์ในลูปเดียวกันได้ โครงงานใช้การจัดรอบควบคุมการเคลื่อนที่ประมาณ 50 Hz และส่ง encoder ทุก 100 ms แต่มีการเรียก `Serial.readStringUntil()` ซึ่งรอ newline หรือ timeout จึงควรพิจารณาผลต่อเวลาตอบสนองเมื่ออธิบายว่า firmware ทำงานแบบไม่บล็อกทั้งหมด

ระบบยังใช้ timeout และสถานะ fault เพื่อรับมือกรณีไม่พบ encoder movement หรือข้อมูล feedback ไม่สดใหม่ เมื่อการเคลื่อนที่ล้มเหลว ซอฟต์แวร์ภารกิจจะหยุดหุ่นยนต์และรายงานข้อผิดพลาด การใช้ state machine ร่วมกับเงื่อนไขหยุดดังกล่าวช่วยให้พฤติกรรมในกรณีปกติและกรณีผิดพลาดตรวจสอบได้ง่ายขึ้น

## 2.6 ระบบจ่ายไฟและวงจรขับกำลัง

ระบบใช้แบตเตอรี่ลิเธียม 12 V 15 Ah เป็นแหล่งจ่ายหลัก มีสวิตช์และ bus bar สำหรับกระจายไฟ วงจร L298N ขับมอเตอร์ ส่วน Step Down DC-DC Buck 10 A และตัวแปลง DC-DC แบบอะแดปเตอร์ที่ติดตั้งอยู่ปรับแรงดันให้เหมาะกับอุปกรณ์ควบคุม คอมพิวเตอร์บอร์ดเดี่ยว และจอสัมผัส การอธิบายสายจ่ายไฟรายอุปกรณ์ต้องอ้างอิงการต่อจริง เพราะรายการอุปกรณ์ยืนยันว่ามีตัวแปลง แต่ไม่ได้ระบุเอาต์พุตและการแยกสาขาทั้งหมด

## 2.7 งานวิจัยและโครงงานที่เกี่ยวข้อง

งานที่เกี่ยวข้องสามารถแบ่งเป็นสามแนวทาง ได้แก่ หุ่นยนต์บริการในร้านอาหาร การใช้ LiDAR สำหรับหุ่นยนต์ภายในอาคาร และการปรับเทียบ odometry ของหุ่นยนต์สองล้อ งานกลุ่มแรกช่วยเปรียบเทียบเป้าหมายการใช้งาน ส่วนอีกสองกลุ่มช่วยอธิบายเทคนิคที่เกี่ยวข้องกับการเคลื่อนที่และความปลอดภัย

| งานที่เกี่ยวข้อง | แนวทางสำคัญ | ความเชื่อมโยงและความแตกต่างกับโครงงาน |
|---|---|---|
| Yang (2021), หุ่นยนต์ภายในอาคารด้วย ROS และ LiDAR [9] | ใช้ LiDAR สองมิติและ particle-filter SLAM เพื่อสร้างแผนที่ และใช้ A* กับ DWA สำหรับนำทาง โดยทดสอบใน simulation | เกี่ยวข้องกับการใช้ LiDAR และ ROS แต่โครงงานนี้ใช้ encoder odometry กับเส้นทางแบบ waypoint เป็นหลัก และใช้ LiDAR เป็น safety guard; ไม่ควรอธิบายว่าใช้ A*, DWA หรือ SLAM localization ในภารกิจหลัก |
| Nguyen และ Nguyen (2025), หุ่นยนต์บริการร้านอาหารด้วย LiDAR-SLAM [10] | ผสาน LiDAR, wheel encoder, accelerometer และ gyroscope เพื่อทำ localization/SLAM และปรับเส้นทางเมื่อมีสิ่งกีดขวาง | มีบริบทการเสิร์ฟอาหารใกล้เคียงกัน แต่ระบบดังกล่าวใช้ sensor fusion และ SLAM สำหรับ localization ส่วนโครงงานนี้มีขอบเขตการนำทางแบบกำหนดเส้นทางและการตรวจสิ่งกีดขวางด้านหน้า |
| Borenstein และ Feng (1996), การวัดและแก้ความคลาดเคลื่อน odometry [6] | วิเคราะห์ความคลาดเคลื่อนเชิงระบบจากระยะห่างล้อและขนาดล้อ พร้อมเสนอวิธีวัดและปรับเทียบ | ใช้เป็นหลักฐานสนับสนุนข้อจำกัดของ dead reckoning และเหตุผลที่ควรวัดความแม่นยำของระยะทางกับมุมเลี้ยวของหุ่นยนต์จริง |

จากการเปรียบเทียบ โครงงานนี้มุ่งแสดงการบูรณาการระบบฝังตัวหลายระดับ ได้แก่ firmware ควบคุมมอเตอร์ การอ่านเซนเซอร์ การสื่อสารกับคอมพิวเตอร์ระดับสูง และการจัดการภารกิจ มากกว่าการพัฒนาระบบ SLAM หรือ path planning ขั้นสูง

## 2.8 สรุป

ทฤษฎีหลักของโครงงานประกอบด้วยระบบฝังตัว, GPIO และ interrupt, PWM, PID, Differential Drive odometry, I2C สำหรับ Keypad ผ่าน PCF8574, Serial และ FSM ส่วน LiDAR safety guard ใช้หยุดการเคลื่อนที่เมื่อพบสิ่งกีดขวางด้านหน้า ผู้ใช้ยืนยันการวางและรับอาหารผ่าน POS/Kiosk หรือ Keypad โดยไม่มี IR sensor ตรวจอาหาร การแบ่งหน้าที่ระหว่าง Arduino Uno กับ Raspberry Pi ทำให้การควบคุมมอเตอร์ระดับล่างเชื่อมกับระบบจัดการภารกิจและส่วนติดต่อผู้ใช้ระดับสูงได้
